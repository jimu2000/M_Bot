## 未实现的菜单项（9 项）

| 编号 | 菜单项 | 原因 |
|---|---|---|
| 11 | 开放云面板端口 | R-Bot 的客户端面板端口（9527）开放。本克隆没有 9527 面板（Web 面板是阶段 3），无端口可开。等阶段 3 有了 Web 面板再接（OCI 安全组 + UFW 放行）。 |
| 14 | 客户端管理 | 管理 R-Bot 客户端进程（r_client）的启停/升级。本克隆没有客户端进程对应物；等阶段 3 Web 面板落地后，改为管理机器人自身的部署状态。 |
| 16 | 监控（自动换 IP） | 实例故障时自动换 IP。需要先定义“故障”判定（ping 不通？SSH 不通？API 状态异常？）与换 IP 频率上限，误判会频繁换 IP 导致服务中断。需用户定判定规则后再做。 |
| 23 | 占用 25% 内存 | R-Bot 的内存占用功能（推测用于保活/占位）。用途不明确，且主动占内存与免费层小内存实例冲突。需用户确认用途后再决定做不做。 |
| 24 | 清除缓存和占用 | 与 23 配对（释放 23 占用的内存）。23 没做，24 也无从做起。 |
| 27 | 一键禁用被封账户 | 禁用被 Oracle 封禁的账号。禁用账号是不可逆的租户级操作，且“被封”的判定需要人工确认，机器人自动禁用风险太高。建议保持人工在控制台处理。 |
| 28 | 删除当前 API | **故意不做**：删除机器人正在用的 API 密钥等于自杀，删完机器人立即失联且无法自愈。R-Bot 有这功能是因为它有多客户端/多 API 可切换；本克隆单机器人进程，删 API 没有安全做法。 |
| 31 | 重启 | 重启机器人自身进程。进程内自杀后无人拉起，必须有 systemd 等守护进程配合。等部署方案定下来（systemd 服务）后再接：机器人退出时 systemd 自动重启。 |
| 32 | 升级客户端 | 升级 R-Bot 客户端二进制。本克隆是 Python 源码部署，升级 = git pull + 重启服务，与阶段 3 的部署方案一起定。 |

## 后续工作（按优先级）

1. **真实 Telegram 联调**：等用户提供机器人 Token，按
   `docs/verification-phase2.md` 的“需 Token 后再测”清单逐项验证。
2. **部署**：机器人应跑在自己的服务器上，用 systemd 托管
   （VM 替换后长跑进程会死，Muse 这边不适合长期跑）。部署时填好：
   - 环境变量 `RBOT_TELEGRAM_TOKEN`、`RBOT_ALLOWED_USERS`
   - `tgbot/config.py` 的 PROFILES（多账号时取消 ACCOUNT2 注释并填真实值）
   - `handlers_extra.py` 的 BOOT_PRESETS（真实镜像/子网/AD/SSH 公钥文件）
   - `~/.oci/config` 与 API 密钥（服务器上配好，机器人只调 OCI CLI）
3. **公开前清理**：`docs/rbot-live.md` 与 `docs/verification.md` 含少量真实
   IP，公开到 GitHub 前必须脱敏（见 verification-phase2.md）。
4. **阶段 3**：Web 面板 + Web SSH 终端（FastAPI + Paramiko + xterm.js），
   参考 `docs/web-ui.md` 与 `docs/screenshots/`。
